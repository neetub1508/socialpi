SocialPi · Deployment architecture

How the stack runs, where it runs, and what it costs

Railway works for v1 — but only after two components are swapped out. Both are blocked by the same constraint, and both turn out to be unnecessary at launch.

Researched 12 Aug 2026 Target: Railway Verdict: viable for v1

Answer first: can we use Railway?

Yes for v1 — but not with the stack exactly as audited. Railway prohibits privileged containers, blocks Docker daemon access, prevents container-runtime installation, and gives no SSH to the host. That is deliberate, and Railway has said there are no plans to change it.

Two components break on that constraint: self-hosted Trigger.dev, whose supervisor launches each task as a new container, and self-hosted E2B, whose Firecracker microVMs need /dev/kvm. Replace the first with pg-boss; drop the second entirely until the agent actually executes untrusted code.

The two blockers

What breaks, and what replaces it

ComponentWhy it breaksResolution for v1
Trigger.dev
self-hosted		 The v4 supervisor launches every task run as a new container. It ships a Docker Socket Proxy rather than raw socket access, but the proxy still has to reach a real Docker daemon on a host you control. Railway provides none. Use pg-boss — a Postgres-backed durable queue using SKIP LOCKED, with ACID guarantees and no extra infrastructure. Runs as an ordinary Railway service.
E2B
self-hosted		 Firecracker needs read/write access to /dev/kvm — bare metal or nested virtualisation. Self-hosting also means a Terraform + Nomad + Consul control plane, GCP minimums of 2,500 GB SSD and 24 vCPU, and a reported ~$1,250/month floor. Deploy no sandbox at all in v1. Add E2B Cloud (managed, pay-per-use) only when the agent writes and runs its own code.

The sandbox question is really a scope question

E2B exists to isolate untrusted, model-generated code. Look at what v1 actually does — compose a post, generate an image, publish it, occasionally drive a browser. None of that executes arbitrary code.

Browser automation with Playwright and browser-use runs perfectly well in a standard unprivileged container. No KVM, no Firecracker, no privileged mode. So v1 ships a plain browser-worker service on Railway, and the sandbox arrives only when the threat model changes.

Licence note: self-hosted Trigger.dev v4 bundles MinIO (AGPL-3.0) by default for large payloads — a second reason to defer it. If you adopt it later, point its object storage at S3/R2 instead.

Decisions

Triggers to leave Railway, and what to resolve first

Watch for these rather than guessing when to migrate:

  • Sandbox spend consistently above ~$1,250/month — bare metal now beats managed E2B.
  • A region Railway does not offer — data residency for EU or India customers.
  • Egress above ~1 TB/month — $100+/month in transfer alone.
  • Any other need for privileged containers — the constraint recurs; plan one move rather than repeated workarounds.

Until one of those fires, Railway's operational simplicity is worth more than the savings.

Open questions before committing

  • Stable egress IP — some platform APIs allowlist source addresses. Confirm whether Railway can provide a static egress address for connector, or whether that forces a proxy. Resolve this first.
  • Data residency — four Railway regions. Confirm coverage if EU or India residency is required.
  • Postgres backups — take independent off-platform backups from day one.
  • Browser-worker geography — automation against geo-restricted content may need specific egress location.
